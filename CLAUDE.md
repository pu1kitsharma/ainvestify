## What this is

**Implementation update (2026-09-13):** User explicitly rejects requiring company/directory URLs. The default UI/dashboard/CLI sourcing path now takes the full brief and optional geography, plans queries using local Ollama, discovers destinations through free public search adapters, then collects original-page evidence. `agents/web_discovery.py` adds DuckDuckGo HTML and Mwmbl API fallback; provider failures remain visible and regional catalog fallback is explicitly limited coverage. Robust entity resolution/corroboration, representative source coverage and selection calibration remain outstanding. See README and architecture §16.14.

An AI-driven, multi-agent system for sourcing and incubating early-stage tech companies, then helping them raise institutional funding — the way a boutique investment bank packages a raise, not a fund screening deals for its own book. The lifecycle: **source** candidate companies (Deal Sourcing Agent, §5.8) → a human reviews and **promotes** a lead into an actual deal → **ingest** the company's own documents (pitch deck, financials) → **extract** structured metrics with mandatory citations → **human review** → **research** external corroboration → **compile** a cited, reviewable memo. That memo is the actual work product used to help the company raise from institutional investors — which is exactly why the guardrails below (citations, cross-checks, mandatory human sign-off) matter *more* here, not less: this output leaves the building and goes in front of outside investors, not just an internal investment committee. The full architecture is in `deal_automation_architecture.md` in this same folder — read that before making any design changes, and update it (don't fork a second design doc) when a real decision changes something in it.

This system supports that process with cited data and a reviewable memo — it does not itself contact investors, negotiate terms, or run the raise. That stays a human-led relationship/advisory activity. Clarified explicitly by the user: this stays the default behavior (nothing here should assume or build toward the system actively contacting investors), but the user is open to revisiting a more active role in a future phase -- that would be its own explicit, separately-scoped decision, not something to infer from this note or build toward speculatively.

No AWS, no cloud of any kind (not even free-tier) until Phase 0 proves the architecture on local hardware. This machine has no dedicated GPU — CPU-only inference via Ollama is the target runtime for this phase (architecture doc §14).

## Locked-in decisions — do not relitigate silently; flag it explicitly if one of these needs to change

- Product is meant to eventually be sold to funds / boutique IB-PE shops, not a single-user personal tool. Design for multi-tenancy from the start even though Phase 0 is single-user (architecture doc §9).
- The business model is sourcing + incubation + fundraising support (boutique-bank-style, helping a company raise from institutional investors), not a fund screening deals for its own investment decisions. Clarified explicitly by the user — see "What this is" above. This doesn't change the pipeline mechanics (ingest/extract/review/research/compile all work the same either way) but it does mean the compiled memo is external-facing collateral, which is the reason the citation/review guardrails are non-negotiable rather than a nice-to-have.
- Human review/sign-off gate before any memo is finalized is **mandatory**. "Automate the grunt work" is the framing that was explicitly chosen over full autonomy — never build toward removing the review gate without a new, explicit decision from the user.
- Market-research data sourcing must be **$0** — no paid APIs/tiers, ever, without a new explicit decision. Apollo is excluded entirely: its API terms of service prohibit embedding it in a product served to other customers, free tier or paid — that's a legitimacy problem, not just a cost one (architecture doc §10.4). Clarified explicitly by the user: this stays the default (nothing paid gets added silently), but the user is open to a paid source for a specific high-value piece if a real case for it comes up — that's still a new explicit decision made per-source, not a blanket lift of the $0 rule.
- Data privacy for deal documents is a hard constraint; infra hosting location is otherwise flexible (architecture doc §8.3).
- Temperature=0 is used for reproducibility only — it is **not** a hallucination guardrail. The actual guardrails are: mandatory source provenance on every extracted number, an independent cross-check pass, and the human review gate (architecture doc §7).
- Every extracted numeric field must carry a source citation (`source_block_id`/`source_page`, or `source_url` for research findings) — a field with no source stays `null`, it is never inferred from "typical" values (architecture doc §6, §7).

- `local_llm_benchmark.py` — run this first to measure real tokens/sec on this machine for candidate models (Ollama-based, CPU-only, no GPU/cloud needed). Let the results drive which model handles which agent role — don't just reuse the ballpark figures in architecture doc §14.1, those are from other people's hardware.
- `schemas.py` — the data model (§6.1 entities, §6.2 extraction schema, §6.3 persistence) as Pydantic models, shared by every agent. Includes `Deal`/`DealStatus` (the Planner's state machine) and consistent `tenant_id` on every entity.
- `store.py` — SQLite persistence layer (§6.3). Every read method is tenant-scoped in the SQL itself (`WHERE tenant_id = ?`), not just by caller discipline — a wrong `tenant_id` for a real id returns nothing, verified live across two tenants. Built now rather than "later": the Planner's interrupt/resume can't be real without something surviving a process restart.
- `agents/planner_agent.py` — Planner/Supervisor Agent (§5.1). Deterministic state-machine routing for the happy path (`sign_mandate → ingest → extract → review → research → compile`); `llama3.2:3b` classifies free-text revision directives into one of the valid actions for the deal's current state (hard-falls-back to the deterministic default if the model proposes something invalid). The planner's own routing decision requires human confirmation before executing, not just the specialist agents' outputs — validated live with a real, non-auto-confirmed run. Also owns `source_leads()`/`source_ib_targets()`/`promote_lead_to_deal()` (pre-deal sourcing, §5.8) and `_run_sign_mandate()`/`_run_add_investor()`/`_run_view_demand_book()` (Origination + Roadshow, §5.1 addendum/§5.9) — the whole lifecycle from sourcing through compilation is this one module's responsibility.
- `main.py` — the "prompt the agent" entry point. `python3 main.py "<free text>"` classifies the request into `source_leads` or `screen_deal` (both dispatched through `agents/planner_agent.py`, which owns the whole lifecycle — sourcing was previously called directly from here, now goes through the Planner's `source_leads()`/`promote_lead_to_deal()`) using the same small-model classification pattern as the Planner. Sourcing extracts both the sector keyword AND an optional geography filter fresh from the prompt (global/unscoped unless a geography is explicitly named), and always prints an explicit scope note that it doesn't run the actual raise (contacting investors, term sheets) — that stays human-led.
- `agents/ingestion_agent.py` — deterministic PDF (pdfplumber) / Excel (openpyxl) parsing into cited `DocBlock`s. No LLM involved, by design (§5.2).
- `agents/extraction_agent.py` — Structured Extraction Agent (§5.3): LLM call with JSON-schema-constrained output, plus the citation-enforcement and cross-check guardrails run in code, not just prompted for.
- `agents/review_checkpoint.py` — Human Review Checkpoint (§5.5/§12): Phase 0 is a CLI stand-in for the eventual review screen (no web UI yet), but the actual mechanics are real — per-field approve/edit/reject, bounded 2-retry reject loop that re-invokes the Extraction Agent with the reviewer's note, full audit trail, and `is_ready_for_compilation()` as the hard gate before Compilation can run. Also reviews `cap_table`/`funding_history` as block-level items now (they weren't originally in the loop — fixed because Compilation must only arrange approved data, including those two).
- `agents/analytics_agent.py` — Analytics/Visualization Agent (§5.6): deterministic matplotlib charts against *approved* fields only, no LLM. Skips a chart template (not a stub) when its required fields aren't approved/extractable.
- `agents/compilation_agent.py` — Compilation Agent (§5.7 + addendum). Produces the real three-document suite, not one generic memo: `compile_cim()` (the original comprehensive memo, full financials/cap table/funding history/external signals, NDA-gated), `compile_teaser()` (anonymized 1-2pg pre-NDA document — excludes cap table/funding history/external signals entirely, not just the company name, and requires explicit human sign-off that it doesn't leak identity before `MemoVersion.approved_by` is set), and `generate_proforma_projection()`/`compile_proforma_document()` (deterministic forward projection with an explicit assumptions list and a `PROJECTED, NOT EXTRACTED` banner — computes numbers rather than arranging them, so it gets its own guardrail language, never LLM-generated). All three hard-refuse (`CompilationBlockedError`) if `is_ready_for_compilation()` is false. The CIM's one LLM call (a narrative paragraph) is still discarded outright if it contains any digit.
- `agents/research_agent.py` — Market Research Agent (§5.4): live lookups against the zero-budget §10.1 sources (GitHub, HN/Algolia, SEC EDGAR, Wikipedia — no key needed, but SEC EDGAR and Wikipedia both require a real identifying User-Agent, see `RESEARCH_AGENT_CONTACT` below) plus FAISS+`bge-large` RAG over `research_corpus/sector_notes.json`. Every finding goes through `review_research_findings()` (in `review_checkpoint.py`) before it can reach a memo.
- `research_corpus/sector_notes.json` — small hand-authored seed corpus (SaaS + hardware/robotics benchmark notes) for the sector-notes RAG. Phase 0 has no real multi-deal corpus yet; this proves the retrieval mechanism, not real accumulated firm knowledge — should grow from real prior deals over time.
- `agents/sourcing_agent.py` — Deal Sourcing Agent (§5.8). Distinct from `research_agent.py`: outputs a `SourcedLead`, never touches `ExtractionResult` until a human promotes a lead to an actual deal (`agents/planner_agent.promote_lead_to_deal()`). Two distinct sourcing modes, kept as separate functions since they target different company types: `discover_leads()` (VC-style, early-stage — GitHub repos by *creation* date + HN "Show HN" launches, dynamic keyword/geography, clone/spam-deduped) and `discover_ib_targets()` (IB-style, mature/public companies — SEC EDGAR full-text search for M&A-process language like "exploring strategic alternatives," validated live against real filings from Bakkt Holdings, Green Dot Corp, OneSpan, Everi Holdings). See §10.6 for why VC-style coverage is still only two sources — the excluded ones (YC's undocumented endpoint, Product Hunt, DuckDuckGo scraping, MCA scraping, UpForge, campus portals) failed the same legitimacy bar regardless of how the request is phrased.
- `sample_docs/` — synthetic test fixtures only (a generated fact-sheet PDF). Real founder-submitted decks still needed for real validation — see next steps.

**Config:** set the `RESEARCH_AGENT_CONTACT` env var (format: `"YourOrg contact@email.com"`) before relying on SEC EDGAR or Wikipedia lookups beyond local smoke-testing — both enforce a real identifying User-Agent per their own published policies (Wikipedia returns a hard 403 without one; confirmed during Phase 0 testing). Left as a placeholder by default rather than defaulting to any real person's contact info.

## Known model/API-behavior findings from Phase 0 (real evidence, not assumptions)

- `phi4-mini` extraction is flaky specifically on `cap_table_source_block_id` — correctly cites it roughly 2 of 3 runs against the same synthetic doc, omits it the rest of the time (causing the whole cap table to be correctly rejected by the citation guardrail, not silently kept). Worth tracking as real accuracy evidence for the Phase 0→1 decision gate (§13) if it keeps showing up on real decks.
- A generic `Any`-typed Pydantic field in a JSON-schema-constrained Ollama call can bias the model toward `null` (see git history / `agents/extraction_agent.py` `LLMValue` comment) — pin concrete types (float/int/str) in any future schema-constrained call, don't use `Any`.
- GitHub's repo search, sorted by star count on a plain keyword query, surfaces whatever popular unrelated repo happens to mention the term rather than the actual company's repo (confirmed: searching "anthropic" that way returned `langchain`). Fixed by requiring the term in the repo name (`in:name` qualifier) and using default relevance sort instead — any future free-text-search connector against a public API should default-sort by relevance, not by a popularity metric, unless the query is already narrow.
- Wikipedia's REST API 403s on the `requests` library's default User-Agent — it enforces the same "descriptive identifying UA" policy SEC EDGAR does, it just doesn't say so until you hit it. Both are handled via the same `RESEARCH_AGENT_CONTACT` setting now.
- GitHub's repository-search endpoint does not support a `location:` qualifier (confirmed live: adding it to a repo-search query silently returns zero results rather than erroring — `location:` only works on user/org search). Filtering repo results by owner location requires a second `/users/{username}` lookup per candidate; see `agents/sourcing_agent.py`'s `_owner_location()`. A source floated in `gemini.md` repeated this exact mistake — worth re-verifying any search-API qualifier against real results before trusting a written suggestion, including one from another AI.
- A bulk find-and-replace across a file (adding `tenant_id=tenant_id,` before every `deal_id=deal_id,`) missed one call site whose indentation didn't match the search pattern (a `ResearchFinding(...)` inside a nested class method, indented 16 spaces instead of 12). Caught immediately by a Pydantic "field required" error on first live run, not silently — but worth grep-verifying every call site individually after a sed-style bulk edit rather than trusting one pattern matched everywhere.
- A state machine's "valid actions per state" table needs the same scrutiny as the states themselves: `DealStatus.COMPILED` initially only allowed `["recompile", "rerun_analytics", "done"]`, which meant a revision request about a field (exactly the architecture's own "redo the ARR chart" example) would silently fall back to "done" instead of routing the fix — caught only by actually testing that exact scenario, not by reviewing the code.
- GitHub repo search results can include the *same repo name* under many different owner accounts — confirmed live on a "fintech" search returning 9 accounts all hosting an identical "Ghostfolio-Open-Source-Wealth-Management-Software" repo. This is the signature of a clone/star-farming spam network, not 9 distinct new companies; a sourcing tool that doesn't dedup by name would surface fake candidates as if they were real leads. Any future discovery connector against a public code-hosting search API should assume this pattern exists and filter for it.
- GitHub's `created:>DATE` qualifier (unlike `location:`) IS valid on repository search and is a meaningfully better "what's new right now" signal than sorting by last-updated — an old repo that got a routine commit yesterday isn't a new company, but one actually created in the lookback window plausibly is.
- `main.py`'s router had two distinct LLM extraction failures on the user's own literal example prompt, caught only by testing that exact prompt end-to-end, not by reviewing the code: (1) `llama3.2:1b` echoed **"europe"** back as the extracted `location_filter` for a prompt that never mentioned any geography — because "europe" appeared as an example value inside the router's own instruction prompt, and the model parroted its own few-shot example instead of extracting from the user's text. Lesson: never put a real-world-plausible example value in an extraction prompt if there's any risk the model echoes it. (2) Switching to `llama3.2:3b` fixed keyword extraction (1b consistently returned no `sector_keyword` at all for this prompt) but introduced a second failure: it labeled **"right now"** — real prompt text — as a geography. Fixed both with defense-in-depth code checks in `classify_prompt()`, not just better prompting: reject any `location_filter` that isn't a literal substring of the user's own text (catches fabrication), AND reject a fixed set of known non-geographic words even when they are real substrings (catches misclassification, e.g. temporal phrases). `main.py` now uses `llama3.2:3b` for this specific open-ended extraction task. (Superseded a few sessions later: `planner_agent.py`'s own directive classifier hit the identical class of failure and was upgraded too — see the entry below.)
- `planner_agent.py`'s `PLANNER_MODEL` was `llama3.2:1b` and worked fine for the deterministic "continue" path (which never calls it) and for the original simple 2-3-option routing tests. Once the valid-action set grew to 5 options (after adding `compile_teaser`/`compile_proforma`), it misclassified "generate the anonymous teaser" as `rerun_extraction` — confirmed live, and confirmed live that `llama3.2:3b` gets the same input right. This silently wiped an already-reviewed `ExtractionResult` and forced a full re-review, which is exactly the kind of mistake the HITL confirmation step exists to catch (a human would have rejected "Proposed action: rerun_extraction" for a teaser request) -- but the test run that surfaced it used `auto_confirm=True` to move faster, which bypassed that safety net. Real lesson: `auto_confirm=True` is for testing the deterministic happy path, not for validating free-text classification quality -- that needs a human (or a real confirmation check) in the loop. Fixed by moving `PLANNER_MODEL` to `llama3.2:3b`.
- `_run_compile_proforma`'s optional growth-rate override crashed with an unhandled `ValueError` on non-numeric input (surfaced by a stdin-timing artifact in a test, not a deliberate adversarial input, which is exactly why it's worth fixing generally) — now caught and falls back to the extracted rate with a warning instead of crashing.
